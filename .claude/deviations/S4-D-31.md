# S4-D-31 — Bedrock + Foundry OpenAPI tool specs (written, not yet run)

Ticket: "Write (do not run) Bedrock + Foundry OpenAPI tool specs pointed at
the proxy." Delivered as `adapters/bedrock/` (YAML + README),
`adapters/foundry/` (JSON + README), and an updated `adapters/README.md`.
Nothing was run; no external service was called. Decisions that diverge from,
or fill gaps in, the ticket's stated ground truth are recorded here.

## 1. There is no OpenAPI document in biject-contracts — this is the first rendering

The proxy's CLAUDE.md says its §8 routes are "named to match the OpenAPI spec
in `biject-contracts`". Checked at authoring time: `biject-contracts/schemas/`
holds four JSON Schemas (`tool_call`, `verdict`, `audit_entry`, `judgement`)
and **no OpenAPI document exists anywhere in that repo**. These two specs are
therefore the first OpenAPI rendering of the §8 tool surface. They were
authored from the enforcement-side ground truth instead:

- `biject-proxy/src/extract.rs` — the `WriteItemCorrection`
  `deny_unknown_fields` struct (six camelCase fields), `ItemPath::parse`
  (six `/`-joined segments, each 1-64 chars of `[A-Za-z0-9_-]`),
  `validate_oid`;
- `biject-proxy/src/lib.rs` — routes, the `x-biject-agent-id` requirement,
  `studyOid` query param, response construction;
- `biject-proxy/src/deny.rs` / `src/forward.rs` — the 403 denial shape
  (eight-value `reason` enum) and the 502 gateway-error shape;
- this repo's `contracts/tool_calls.json` (DRAFT v0) for constraints the
  proxy structs leave to the verifier (`newValue` ≤ 4000, `actorId`
  identifier pattern, `reasonCode` 0-7, `sigEd25519` 88-char base64).

If/when biject-contracts grows a canonical OpenAPI document (S4-A-12 freeze or
later), that document supersedes these; they must be reconciled against it and
must never drift from the vendored JSON Schemas in the meantime.

## 2. Two shape decisions where sources disagree

- **`studyOid` / OID segment length: 64, not 256.** DRAFT v0's `oid` allows up
  to 256 chars; the proxy's `validate_oid` rejects anything over 64. The specs
  advertise 64 — advertising what the enforcement point refuses would be a
  lie in the permissive direction. Flag for the S4-A-12 freeze to pick one.
- **`reasonCode`/`sigEd25519` tighter than the proxy struct.** The proxy
  deserializes `reason_code` as any `u32` and `sig_ed25519` as any `String`;
  the kernel/contract is what constrains them. The specs carry the DRAFT v0
  enum (0-7) and signature pattern so a generated tool schema gives the model
  the closed sets, which is the direction §2B.1 wants.

## 3. `X-Biject-Agent-Id` is not an operation parameter

Both routes require the header; both specs document it in `info`, per
operation, and on the 403 response — but deliberately do **not** model it as
an OpenAPI parameter. A header parameter in a Bedrock/Foundry tool schema
becomes a model-fillable input, and the calling agent's identity must never be
a value the model chooses (it is what the verdict is attributed to in the
signed ledger). Each README records the intended platform mechanism for
injecting it (Bedrock: API-key credential provider with header location;
Foundry: custom-keys connection) — both unexercised.

## 4. The write tool is fail-closed but non-functional through these specs

`actorId` / `tsUnixMs` / `sigEd25519` are harness-signed (S4-A-30), never
model-chosen. An OpenAPI tool surfaces all six body fields to the model, so a
model-driven call would carry a fabricated signature, fail kernel
verification, and be denied — safe, but not useful. Both READMEs state this
outright instead of implying the write path would work. The signing injection
point (gateway interceptor, fronting service, or in-proxy signing) is an open
design question deliberately left open, mirroring the hard-stub
`build_audit_entry` decision in `adapters/openai/tools.py`.

## 5. Format and anti-drift

One spec, two renderings: Bedrock is YAML (idiomatic for AWS tooling), Foundry
is JSON (the `azure-ai-agents` examples `json.load` the spec) and is
**generated from the YAML** — identical `paths`/`components`, only the `info`
block differs. OpenAPI 3.0.3 was chosen over 3.1 as the lowest common
denominator both importers are documented to accept (unexercised, like
everything else here).

## 6. Placeholder server

No deployed demo domain exists (S4-D-10 has not run). The server entry is
`https://{demoDomain}` with a server-variables block whose default,
`biject-proxy.pending-s4d10.invalid`, is an RFC 2606 reserved name that can
never resolve — a fabricated-but-plausible hostname was explicitly ruled out.
The Foundry README additionally warns that some importers do not expand server
variables, so substitution is a pre-import step.

## 7. Overclaim audit

Performed before commit, as the ticket requires: grepped the new/changed files
for tested / validated / verified / verify / compatible / works with /
confirmed / supports. Remaining hits are (a) the platform's own enforcement
vocabulary ("verification proxy", "verified before forwarding"), which
describes what the *proxy* does, not any Bedrock/Foundry compatibility; (b)
explicit negations ("has never been exercised", "do not represent them as
validated"); and (c) the pre-existing, sanctioned public claim about the
OpenAI adapter in `adapters/README.md` (unchanged by this ticket). Every
statement about Bedrock or Foundry behaviour is qualified as design intent
from documentation, with a "What has NOT been established" checklist in each
README.
